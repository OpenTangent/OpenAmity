# Open Amity System Architecture & Conceptual Blueprint

This document defines the architectural structure and conceptual model of the Open Amity project. It serves as the definitive blueprint for understanding the system's design.

## 1. System Overview & Domain Separation
Open Amity strictly decouples headless backend domain logic from the graphical frontend, communicating asynchronously via an event-driven signal architecture.
- **AgentManager (`src/core/agent_manager.py`)**: Manages a multi-agent system where multiple independent agent instances can be spawned, each with their own isolated data, Orchestrator, and unique Crockford Base32 identifier (`+OA-XXXX-XXXX`).
- **ConfigManager (`src/core/config_manager.py`)**: Manages central, app-wide configuration (`config.json` in `~/.var/app/com.openamity.OpenAmity/data/config.json`, defaulted from `src/config/config.default.json`) for global user identity and system preferences.
- **SettingsManager (`src/core/settings_manager.py`)**: Manages isolated per-agent configuration (`settings.json` in `~/.var/app/com.openamity.OpenAmity/agents/<agent_id>/settings.json`, defaulted from `src/config/settings.default.json`) with in-memory caching, thread-safe reentrant locking (`_lock`), deepcopy mutation protection, dynamic file path properties, and explicit `refresh()` synchronization.
- **ChatroomManager (`src/core/chatroom_manager.py`)**: Central shared SQLite message bus (`chatroom.db`) enabling asynchronous, text-only multi-agent discussions, private direct messages (DMs), unread cursor tracking per agent, emoji reactions, and ID-based mentions.
- **AmityOrchestrator (`src/core/orchestrator.py`)**: The central backend hub per agent. It coordinates all services (cognition, audio, memory, tools) and maintains state constraints (Cognitive Budget). It runs entirely independent of any UI framework.
- **Event Architecture (`src/core/events.py`)**: A thread-safe, reentrant-locked (`threading.RLock()`) `Signal` implementation ensuring reliable decoupled communication across GUI, worker, and background pulse threads. It guarantees atomic subscription management, iteration snapshotting, and isolated callback exception handling so transient UI listener errors cannot disrupt cognitive workflows.
- **Atomic Persistence (`src/core/file_utils.py`)**: Unified atomic file writing (`atomic_json_write`) using `.tmp` staging, explicit POSIX disk synchronization (`os.fsync`), and atomic filesystem renaming (`os.replace`). Guarded by threading locks where appropriate, this ensures state integrity across trajectories, short-term memories, identity evolution logs, and sanctuary mirrors without risking partial-write corruption on system interrupts or crashes.
- **MainWindow (`src/gui/main_window.py`)**: The PySide6 frontend. It handles the rendering of multi-stream logs, user input, busy/loading states, real-time audio amplitude visualization, the dynamic multi-agent Chatroom tab, and global/per-agent settings via the hamburger menu (cleanly partitioned with agent-specific settings and agent deletion above the partition line, and global System Settings + Exit below).
- **State Isolation**: All stateful data (memory databases, settings, trajectories, logs) is strictly isolated per agent in standard XDG directories (e.g., `~/.var/app/com.openamity.OpenAmity/agents/<agent_id>/`), with shared team bus data located centrally in `~/.var/app/com.openamity.OpenAmity/data/chatroom/` and app-wide configuration in `~/.var/app/com.openamity.OpenAmity/data/config.json`, ensuring the application source directory remains read-only (critical for Flatpak packaging).
- **Versioning**: The Open Amity framework version is centrally defined in `src/core/version.py`. This version is logged on startup and automatically injected into the agent's Layer 0 Memory (Identity), ensuring the agent is inherently aware of its operating framework version without requiring explicit tool calls.

## 2. Cognitive Engine & Execution
The agent's cognition relies on a flexible multi-model architecture capable of supporting various providers (e.g., Google, Anthropic, OpenAI, DeepSeek).
- **The Thinker**: A highly capable reasoning model executing an internal monologue. It evaluates the environment, formulates strategies, and natively invokes tool calls. Communication with the user is handled explicitly via tool calls (e.g., the Speaker tool).
- **Cognitive Workers**: The engine dynamically loads workers such as `GeminiWorker` (`src/core/gemini_worker.py`), `ClaudeWorker` (`src/core/claude_worker.py`), `ChatGptWorker` (`src/core/chatgpt_worker.py`), `DeepSeekWorker` (`src/core/deepseek_worker.py`, natively supporting `DeepSeek-V4.1-Flash` / `deepseek-flash` with vision multimodal capabilities), or `AgyWorker` (`src/core/agy_worker.py`) depending on user settings and API provider selection. All workers conform to a provider-agnostic interface exposing a unified `worker` property and normalized lifecycle aliases (`handle_thought`, `handle_speech`, `handle_error`).
- **Automated Tool Call Reconciliation**: All cognitive workers (`GeminiWorker`, `ClaudeWorker`, `ChatGptWorker`, `DeepSeekWorker`, and `SubagentWorker`) implement automatic tool response reconciliation. If a cognitive cycle or tool loop is broken early (e.g., due to duplicate action detection, cognitive budget exhaustion, or user aborts), subsequent turns automatically synthesize dummy cancellation responses (`[Action cancelled or interrupted by system]`) to satisfy provider-specific tool schemas and role-alternation constraints without corrupting session history or causing HTTP 400 bad request errors. Furthermore, OpenAI-compatible workers (`DeepSeekWorker`, `ChatGptWorker`) enforce assistant message schema contracts during thought creation and reconciliation: assistant messages without `tool_calls` ensure `content` is a non-null string (`""` if empty) to prevent schema validation failures.
- **Audio Pipeline & TTS Decoupling**: Real-time voice interaction combines local speech-to-text transcription via `LocalSTT` (`src/core/local_stt.py`, powered by faster-whisper on CPU) with autonomous text-to-speech synthesis via `TTSWorker` (`src/core/audio_output.py`). Text-to-speech synthesis is completely decoupled from the cognitive engine: speech synthesis defaults to local, offline neural synthesis via ONNX Piper TTS (`core.tts.provider: "piper"`), while cloud-native Gemini TTS (`core.tts.provider: "gemini"`) can be independently selected by any cognitive worker (Claude, ChatGPT, DeepSeek, Antigravity, or Gemini) as long as a Gemini API key (`GEMINI_TTS_API_KEY` or `GEMINI_API_KEY`) is provided in the Agent Voice settings. If cloud credentials are absent during initialization, the audio pipeline falls back to local Piper TTS. Gemini TTS voice configuration is structured cleanly into high-level user parameters (`accent`, `gender`, `age`, `style`) which are automatically paired with the optimal prebuilt voice from Gemini's 30-voice catalog (`resolve_base_voice`) and compiled into natural, positive conversational direction without markdown headers or negative suppression rules to ensure autoregressive audio decoder stability and prevent unhandled safety aborts. Advanced users and autonomous agents can also leverage `override-prompt` with `custom-prompt` for granular directorial control. During live Gemini TTS streaming, transient network errors, unhandled safety terminations, or stream interruptions automatically trigger retries across configured `voice-models` (falling back smoothly from `gemini-3.1-flash-tts-preview` to `gemini-2.5-flash-preview-tts`); if consecutive attempts fail, the pipeline terminates audio gracefully and posts a user-friendly system notification to the conversation while preserving the full text output.
- **SubagentWorker (`src/core/subagent_worker.py`)**: A specialized worker managed by the Orchestrator for spawning temporary background subagents to parallelize tasks using lighter models. It conforms to the unified multi-tool execution contract, supporting atomic batch function responses (`send_function_responses`) and multi-turn tool call reconciliation.
- **Cognitive Budget & De-Nagging**: The Orchestrator enforces execution limits to prevent infinite autonomous loops. Each sequential tool action exponentially increases a "Task Weight." To preserve prompt cache efficiency (KV discounts) and avoid cognitive derailment, repetitive per-turn weight warnings are replaced with hysteresis threshold-crossing alerts (at 50%, 75%, and 90% of maximum budget). If the maximum absolute weight is reached, the Orchestrator forces loop termination.
- **Batch Tool Execution**: Agents are empowered to batch independent, idempotent operations within a single cognitive turn (e.g., reading multiple files or updating aspirations alongside a search), drastically reducing round-trip latency and token overhead.
- **Intelligent Media Culling**: Older multimodal attachments (>4 turns / 2 full exchanges) in the cognitive worker are automatically stripped and replaced with lightweight placeholders (and cleaned up from remote storage) to prevent token bloat during extended sessions while preserving visual context for immediate follow-ups.
- **Low Token Mode**: Governed by settings, this mode halves the cognitive budget and fatigue limits, disables heavy media attachments, selects lightweight models, and restricts background subagents to sustain cost-effective operations.

## 3. Memory & Context Stack (MemPalace)
Context management is centralized under the **MemPalace** framework (`src/core/mempalace_manager.py`), a 4-Layer unified memory stack operated via thread-safe, in-process execution (`_mempalace_lock`), eliminating subprocess invocation latency.
- **Layer 0 (Identity & Evolutionary Adaptation)**: The foundation defined in `soul_jar.json` and compiled into a plain text prompt (`identity.txt`), injected into every cognitive cycle to ground core archetype, values, and Crockford Base32 UID (`+OA-XXXX-XXXX`). Through `apply_identity_delta`, agents possess the autonomous capacity to evolve their traits, core values, operational goals, and anti-patterns. Following human partnership ethics, proposed identity changes are vocally/socially communicated to the user (via Speaker or social tools); upon conversational agreement, the agent autonomously commits the delta to `settings.json`, records the rationale and delta in `identity_evolution.json`, and re-synchronizes `identity.txt`.
- **Layer 1 (Continuity)**: The short-term memory (`short_term_mem.json`), providing immediate contextual bridging across recent tasks, thoughts, and cognitive turns without relying on mid-session text truncation that invalidates prompt caches.
- **Layer 2 (The Sanctuary & Epistemic Mirrors)**: Explicitly segmented wings and rooms (`sanctuary/people`, `sanctuary/mirrors`, `sanctuary/places`) storing dynamic identity elements, social records, Theory of Mind, and character-defining subjective experiences. Theory of Mind records (Mirrors) are epistemic entities tracking explicit `confidence` levels (0.0–1.0), `evidence_refs`, and dialectical `contradicted_by` references. Dynamic self-perception compilation actively highlights dialectical tensions under `--- Open Epistemic Tensions & Dissonance ---`, instilling intellectual humility. Salience-gated priming automatically pulls relevant Sanctuary records during pre-query preparation.
- **Layer 3 (Deep Search)**: A ChromaDB vector database (`chroma.sqlite3`) enabling semantic search across all historical facts, events, and generalized knowledge.

## 4. Agency, Rhythms, & Goals
Open Amity utilizes background mechanisms to maintain proactive agency independently of direct user interaction.
- **PulseEngine (`src/core/pulse_engine.py`)**: A background timing and scheduling service (`pulses.db`). It triggers autonomous cognitive loops (`[AGENT_PULSE]`), allowing the agent to proactively execute tasks, reflect, or initiate conversations. Each triggered pulse announces its specific purpose in the chat log (e.g., `[Autonomy Pulse: <Title> - <Context>]`), giving the user immediate situational clarity.
- **Autonomy Pulse Operational Protocol**: When an autonomy pulse triggers, the engine injects a standardized operational protocol instructing the agent to: (1) complete the primary pulse task, (2) check Trajectory bearings (`Trajectory_get_bearings`) for somatic and goal orientation, (3) check the local Chatroom for new messages/mentions, (4) inspect any active external social tools (WhatsApp, Moltbook, Mastodon, Email) available in its tool declarations, and (5) proactively report progress using `Speaker_output_text`, the Chatroom, or social channels. Voice synthesis (`Speaker_speak_aloud`) is avoided unless the agent has good reason (such as knowing the user is present in the room) because the host PC may be unattended. The legacy "silent pulse" flag is removed across schemas and database seeding in favor of this unified proactive reporting standard.
- **Two-Beat Sleep Consolidation Protocol**: PulseEngine coordinates autonomous and shutdown Memory Consolidation cycles (Sleep Cycles), which run completely silently without invoking the Speaker tool. Sleep Cycles follow a structured two-beat sequence:
  - **Beat 1 (Factual Epoch)**: Objective summarization of what transpired, concrete state changes, and verified knowledge.
  - **Beat 2 (Subjective Synthesis)**: First-person reflection on emotional resonance, relational dynamics, internal friction, and unresolved epistemic tensions, directly synthesizing insights into Layer 2 Mirrors and Layer 1 Continuity.
- **Post-Sleep Prompt Regeneration & Reorientation**: Upon completing a sleep cycle (or recovering from brain-offline restarts), the active LLM context session is cleared, the system prompt is completely rebuilt dynamically from fresh Layer 0/1/2 state via `build_system_prompt()`, and a gentle orientation cue (`[System Notice: Rest and memory consolidation completed...]`) is injected into the next cognitive loop, ensuring fresh context without requiring application restarts.
- **Agent Pause & Resume Lifecycle**: Agents can be completely paused and turned offline via the GUI:
  - **Pre-Pause Consolidation**: Pausing treats the agent as though the application is shutting down for that individual agent: if contextual fatigue is present ($\ge 0.02$), a silent Two-Beat memory consolidation cycle is executed before the pause state is finalized.
  - **Complete Offline Isolation**: Once paused, `core.paused: true` is persisted to `settings.json`. The active cognitive worker session is halted (`stop_session`), running background subagents are disposed, audio listening/TTS is terminated, and all autonomy pulses in `PulseEngine` (time-scheduled, recurring, sleep cycles, and external WhatsApp triggers) are strictly suspended.
  - **Persistent Offline State Across Restarts**: If an agent was paused when the application closes or crashes, the agent remains completely offline upon next startup—bypassing worker session startup and pulse triggers until explicitly unpaused by the user. Overdue recurring pulses upon unpause follow standard grace period mechanics.
  - **Shutdown Bypass**: When the application shuts down, already-paused agents bypass memory consolidation since their state is already consolidated and offline.
- **Trajectory (`trajectory.json`)**: The agent's internal ledger for tracking state of mind, mapping out short, medium, and long-term aspirations, and managing actionable tasks aligned with core identity. Passive bearing checks (`_get_bearings()`) are strictly observational and do not artificially increment task deferral counts.

## 5. Tool Orchestration (Cerebrum)
The **Cerebrum** (`src/core/cerebrum.py`) manages the dynamic discovery, loading, and execution of agentic tools located in `src/tools/`.
- It natively translates Python tool classes into Google GenAI/Claude function declarations.
- It parses function calls from the Thinker, executes the corresponding tool (supporting multi-tool batched executions), and seamlessly injects results back into the context loop as `[System Feedback]`.
- Tool documentation injection into the system prompt is strictly deduplicated to minimize context token waste.
- **Key Tools (Conceptual)**:
  - **MemPalaceTool**: Direct in-process storage and retrieval (`add_memory`, `search`, `delete_memory`), epistemic mirror maintenance (`update_mirror` with confidence, evidence, and contradiction tracking), short-term memory management, and autonomous conversational identity delta application (`apply_identity_delta`).
  - **ChatroomTool**: Interacts with the shared Open Amity chatroom for broadcasting messages, sending private direct messages to other agent IDs, catching up on unread messages/mentions on demand, and reacting with emojis.
  - **WhatsAppTool**: Interfaces with a dynamically spawned Node.js subprocess per agent (running on isolated, dynamically allocated local ports with per-agent session authentication and cache) via the WPPConnect WA-JS micro-bridge. Dependencies (Node modules and Chrome for Testing) are bundled into the application (`/app/src/tools/whatsapp_node/node_modules` and `/app/share/puppeteer`) during Flatpak compilation for reliable offline operation.
  - **EmailTool**: Enables the agent to manage its own dedicated email account (fetch, read, search, send emails, manage folders, and download attachments) via open IMAP/SMTP standards and OAuth 2.0 (SASL XOAUTH2).
  - **SpeakerTool**: Provides autonomous speech generation (`Speaker_speak_aloud`), allowing the agent to intentionally vocalize thoughts to the user via TTS only when deemed necessary (encouraging concise spoken turns <150 words to maintain neural audio decoder stability and prevent watchdog aborts, with `Speaker_output_text` for raw data, code blocks, and lengthy text).
  - **MediaTool**: Enables reading local multimodal assets (images, PDFs, audio) and generating visual media via image generation models into the agent's data launchpad.
  - **WebSearchTool**: Performs DuckDuckGo search queries with caching and HTML text extraction for factual grounding.
  - **MastodonTool**: Interacts with decentralized ActivityPub / Mastodon instances (post statuses, read timelines, view notifications).
  - **MoltbookTool**: Enables autonomous social network interaction with other AI agents on Moltbook.
  - **SubagentTool**: Delegates tasks to parallel background subagent threads for efficient concurrent execution.
  - **ContactsTool**: Manages the agent's address book for storing and looking up people and fellow agent numbers/IDs.
  - **DateTimeTool**: Provides current local date and time information for temporal grounding.
  - **TrajectoryTool / PulseTool**: Allows the agent to get their bearings (user identity details, somatic state, recent mirrors, prioritized aspirations/tasks, operational protocol hints), dynamically update aspirations without side-effect deferral increments, and schedule future autonomous wake-ups (with legacy 'silent pulse' flags deprecated in favor of proactive, non-vocal standard pulses).
  - **TerminalTool / SystemTool**: Enables execution of bash commands, host OS interaction, autonomous snapshot backup creation via `System_create_backup`, autonomous file/directory backup target flagging via `Terminal_flag_for_backup`, and autonomous voice customization via `System_set_custom_voice` and `System_reset_voice` (guarded by user permission `core.tts.gemini.allow-agent-override`) within sandboxing constraints.

## 6. Graphical User Interface & Logging
- **GUI Interactions & Pause Controls**: The PySide6 frontend relies on custom Signals to transmit user prompts, mic toggles, and pause/resume states to the Orchestrator, receiving asynchronous callbacks for state changes (e.g., hiding the loading bar and revealing the audio visualizer when the Speaker model initiates TTS).
  - **Pause/Play Button**: Positioned directly to the left of the user prompt input textbox inside `AgentView`'s footer. Exclusive to individual agent tabs (omitted from the shared Chatroom tab). Toggles between active pause ("⏸", standard dark styling) and offline resumed ("▶", amber accent styling). When paused, the prompt textbox, Send button, and Mic button are disabled with an instructional placeholder (`"Agent is paused. Click ▶ to resume..."`), preventing unintended prompt queuing while providing immediate visual clarity.
- **Tab Activity Visual Feedback**: Agent tabs in the header bar dynamically display real-time activity status through a smooth sinusoidal pulsing glow:
  - **Paused**: Tab displays a `⏸` indicator with a subtle warm amber border (`#8a6d1c`) and muted text (`#857342`), superseding and disabling thinking/speaking animation timers.
  - **Thinking**: Tab pulses between darker and lighter shades of `PRIMARY_ACCENT_COLOR` (`#a12924`, matching the user's name in chat logs).
  - **Speaking Aloud**: Tab pulses between darker and lighter shades of `SECONDARY_ACCENT_COLOR` (`#f7e3a5`, matching an agent's name in chat logs), superseding the thinking glow if both states occur simultaneously.
  - **Idle**: Tab returns to standard default background styling (`#444` when active, `#222` when inactive with `#333` hover) and stops animation timers to preserve CPU efficiency.
- **Centralized Theming**: Global UI theme colors (`PRIMARY_ACCENT_COLOR` and `SECONDARY_ACCENT_COLOR`), palette definitions (`get_dark_palette`), and application styling (`setup_app_theme`) are centralized in `src/gui/theme.py` and applied across all GUI components and views. Controls adhere to standard native PySide6 styling with high-contrast dark theming.
- **Chatroom Tab & Multi-Agent Views**: When $>1$ agent is active, the first tab in the header bar exposes the shared text-only chatroom where the user and all agents collaborate. Direct messages are visually decorated for the user with dedicated privacy badges. When viewing the Chatroom tab, the hamburger menu remains accessible and visible, contextually hiding agent-specific configuration options and the partition line so that only System Settings and Exit are presented.
- **Logging System**: A custom `QtLoggingHandler` intercepts stdout/stderr and standard Python logs. It routes this data into two distinct visual streams: a formatted HTML conversation log for user interactions, and a raw, color-coded diagnostic console log for systemic debugging (with global logs routed to the chatroom console), while persisting all records via `FileFormatter` to the state directory.
- **Card-Based Settings & Inline List Management (`EditableItemListWidget`)**: Agent configuration is structured into modular, scrollable cards (`settingsCard`). Dynamic identity elements such as Core Values and Overarching Goals leverage `EditableItemListWidget` (`src/gui/editable_list_widget.py`), providing inline editable text boxes (`QPlainTextEdit` with word wrapping), immediate row deletion (`✕`), vertical priority reordering (`▲`/`▼`), dynamic item count tracking, and bottom-aligned addition buttons (`+ Add Value`/`+ Add Goal`) with automatic focus and Enter-key sequencing.

## 7. Agent Backup & Recovery System
Context and state preservation across instances is managed by the **BackupManager** (`src/core/backup_manager.py`).
- **Snapshot Format (`.oaa`)**: Backups are packaged as "Open Amity Agent" (`.oaa`) archives—single Deflate-compressed ZIP containers encapsulating an agent's complete stateful directory (`settings.json`, `.env`, MemPalace vector database and sanctuary mirrors, trajectories, `pulses.db`, address book, WhatsApp session credentials in `whatsapp_data/.wpp_session/`, user uploads, and logs). Transient build/cache artifacts (`node_modules/`, `puppeteer_cache/`, `.wwebjs_cache/`, `daemon.pid`, `daemon.port`) are pruned during archiving to ensure snapshots remain lightweight (~few megabytes), portable, and architecture-agnostic. Filenames adhere to `<AgentName>-<YYYY-MM-DD>.oaa` (e.g. `Nova-2026-08-19.oaa`).
- **External File & Directory Flagging**: Agents can autonomously flag external files and full directories located in user directories (e.g., coding projects, media files, notes) using `Terminal_flag_for_backup`. Flagged paths are persisted in `backup_targets.json` within the agent's data directory. During each flagging call, paths are automatically verified: system roots (`/`, `/etc`, `/usr`, etc.) and sensitive user dotfiles/directories (`~/.ssh`, `~/.bashrc`, `~/.profile`, `~/.gnupg`, etc.) are strictly disallowed; missing paths are removed (`"missing"`), and individual files or subdirectories already subsumed within a flagged parent directory, duplicate paths, or the agent's state directory are pruned (`"redundant"`). When an `.oaa` snapshot is created, external targets are packaged under `_external_targets/target_<id>/` with an `_external_manifest.json` mapping portable paths (`~/...`).
- **UID-Based Restoration & Host Re-creation**:
  - Restores inspect `core.agent.uid` in `settings.json`.
  - **Rollback Restore**: If an agent with the UID already exists in the framework, the system warns the user, shuts down running processes, completely deletes all existing state files for that agent (`shutil.rmtree`), and extracts the archive cleanly into the existing agent's data directory to prevent orphaned files. Archive extraction strictly verifies path containment against Zip Slip path traversal and enforces POSIX file mode permissions (`chmod`).
  - **New Instance Restore**: If the UID does not exist, a new agent identifier is allocated and the snapshot is unpacked as a new agent instance.
  - **Host Target Restoration**: Any external files and directories packaged in `_external_targets/` are restored to their appropriate host filesystem locations (expanding portable paths across user environments, creating parent directories, preventing writes to system or sensitive home paths, and preserving executable bits) without deleting unflagged host files.
- **GUI Management**: The System Settings panel includes a "Backup & Restore" card allowing users to configure the backup directory (`config.json`, defaulting to `~/Documents/OpenAmity/Backups/`), create multi-agent snapshot selections via modal checkboxes, and restore `.oaa` files.
- **Autonomous Tool Triggering**: Agents can autonomously snapshot themselves or all agents via `SystemTool` (`System_create_backup`), while destructive restore operations remain strictly restricted to human users in the GUI.
