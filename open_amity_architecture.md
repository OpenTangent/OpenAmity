# Open Amity System Architecture & Conceptual Blueprint

This document defines the architectural structure and conceptual model of the Open Amity project. It serves as the definitive blueprint for understanding the system's design.

## 1. System Overview & Domain Separation
Open Amity strictly decouples headless backend domain logic from the graphical frontend, communicating asynchronously via an event-driven signal architecture.
- **AgentManager (`src/core/agent_manager.py`)**: Manages a multi-agent system where multiple independent agent instances can be spawned, each with their own isolated data, Orchestrator, and unique Crockford Base32 identifier (`+OA-XXXX-XXXX`).
- **ConfigManager (`src/core/config_manager.py`)**: Manages central, app-wide configuration (`config.json` in `~/.var/app/com.openamity.OpenAmity/data/config.json`, defaulted from `src/config/config.default.json`) for global user identity and system preferences.
- **SettingsManager (`src/core/settings_manager.py`)**: Manages isolated per-agent configuration (`settings.json` in `~/.var/app/com.openamity.OpenAmity/data/agents/<agent_id>/settings.json`, defaulted from `src/config/settings.default.json`) with multiton deduplication per agent/config directory, unified in-memory caching across subcomponents (Orchestrator, PulseEngine, Tools, GUI panels), thread-safe reentrant locking (`_lock`), deepcopy mutation protection, dynamic file path properties, POSIX atomic disk synchronization (`atomic_json_write`), and automatic external modification detection and explicit `refresh()` synchronization.
- **ChatroomManager (`src/core/chatroom_manager.py`)**: Central shared SQLite message bus (`chatroom.db`, Schema v2) enabling dynamic user-created chatrooms, permissioned agent membership (newly created agents start with zero chatroom access), headless watch notifications with progressive debounce escalation, unread cursor tracking per room and agent, emoji reactions, and room-scoped direct messages.
- **AmityOrchestrator (`src/core/orchestrator.py`)**: The central backend hub per agent. It coordinates all services (cognition, audio, memory, tools) and maintains physiological state constraints (Fatigue & Token Usage Limit). It runs entirely independent of any UI framework.
- **Event Architecture (`src/core/events.py`)**: A thread-safe, reentrant-locked (`threading.RLock()`) `Signal` implementation ensuring reliable decoupled communication across GUI, worker, and background pulse threads. It guarantees atomic subscription management, iteration snapshotting, and isolated callback exception handling so transient UI listener errors cannot disrupt cognitive workflows.
- **Atomic Persistence (`src/core/file_utils.py`)**: Unified atomic file writing (`atomic_json_write`) using `.tmp` staging, explicit POSIX disk synchronization (`os.fsync`), and atomic filesystem renaming (`os.replace`). Guarded by threading locks where appropriate, this ensures state integrity across trajectories, short-term memories, identity evolution logs, and sanctuary mirrors without risking partial-write corruption on system interrupts or crashes.
- **MainWindow (`src/gui/main_window.py`)**: The PySide6 frontend. Features a full-height Chatroom Tabs sidebar on the left with pinned "✦ Agents" (for direct messaging, showing the last selected agent) and dynamic chatroom tabs, an Agent Tabs top bar sorted chronologically by agent age and filtered to members of the selected room, contextual New/Edit room editor panels, and a context-aware hamburger menu (partitioned with agent settings when direct messaging an agent, or Chatroom settings like Edit/Delete Chatroom when viewing a room, with System Settings and Exit below).
- **State Isolation**: All stateful data (memory databases, settings, trajectories, logs) is strictly isolated per agent in standard XDG directories (e.g., `~/.var/app/com.openamity.OpenAmity/data/agents/<agent_id>/`), with shared team bus data located centrally in `~/.var/app/com.openamity.OpenAmity/data/chatroom/` and app-wide configuration in `~/.var/app/com.openamity.OpenAmity/data/config.json`, ensuring the application source directory remains read-only (critical for Flatpak packaging).
- **Versioning**: The Open Amity framework version is centrally defined in `src/core/version.py`. This version is logged on startup and automatically injected into the agent's Layer 0 Memory (Identity), ensuring the agent is inherently aware of its operating framework version without requiring explicit tool calls.

## 2. Cognitive Engine & Execution
The agent's cognition relies on a flexible multi-model architecture capable of supporting various providers (e.g., Google, Anthropic, OpenAI, DeepSeek, OpenRouter).
- **Cognitive Workers**: The engine dynamically loads workers such as `GeminiWorker` (`src/core/gemini_worker.py`), `ClaudeWorker` (`src/core/claude_worker.py`), `ChatGptWorker` (`src/core/chatgpt_worker.py`), `DeepSeekWorker` (`src/core/deepseek_worker.py`, natively supporting `DeepSeek-V4.1-Flash` / `deepseek-flash` with vision multimodal capabilities), `OpenRouterWorker` (`src/core/openrouter_worker.py`, aggregating hundreds of models across providers using a single API key with normalized reasoning and tool calling), or `AgyWorker` (`src/core/agy_worker.py`) depending on user settings and API provider selection. All workers conform to a provider-agnostic interface exposing a unified `worker` property and normalized lifecycle aliases (`handle_thought`, `handle_speech`, `handle_error`). Users can granularly configure the specific primary AI model, thinking level (`low`, `medium`, `high`, `max`), and light model for each provider via the Cognitive Provider panel, with "Custom..." input support for future-proofing. The default thinking level across all providers is `"low"` (mapped to `thinking_budget=1024` in Gemini/SubagentWorker, `output_config={"effort": "low"}` in Claude, `reasoning_effort="low"` in ChatGPT, enabled reasoning in DeepSeek, and `{"reasoning": {"effort": "low"}}` in OpenRouter); low thinking tends to perform better in conversational flow and prevents runaway token consumption, while agents requiring multi-turn problem decomposition can autonomously invoke `System_contemplate`—a no-op filler tool sustaining the autonomous loop within the Open Amity framework with the advantage of clean audit trails. Furthermore, Open Amity employs a unified **Light Model Fallback Architecture**: rather than cycling through arbitrary multi-model fallback lists, all cognitive workers attempt execution with the primary model first. A light model is used strictly and only as a fallback if the standard AI model has reached its quota (e.g. HTTP 429 rate limit or quota exhaustion); non-quota errors (such as 400 bad requests, 404 missing endpoints, or server errors) do not trigger light model fallback. Additionally, if multimodal input fails (such as downstream provider schema rejections or unsupported audio/media), the worker strips the multimodal input, retries the turn on the standard model, and strips multimodal inputs on subsequent turns. Token tracking across all workers isolates per-turn marginal delta tokens (`completion_tokens` + new turn input tokens) rather than accumulating cumulative prompt context, ensuring uniform somatic fatigue tracking.
- **Automated Tool Call Reconciliation**: All cognitive workers (`GeminiWorker`, `ClaudeWorker`, `ChatGptWorker`, `DeepSeekWorker`, `OpenRouterWorker`, and `SubagentWorker`) implement automatic tool response reconciliation. If a cognitive cycle or tool loop is broken early (e.g., due to duplicate action detection, fatigue limit cutoff, or user aborts), subsequent turns automatically synthesize dummy cancellation responses (`[Action cancelled or interrupted by system]`) to satisfy provider-specific tool schemas and role-alternation constraints without corrupting session history or causing HTTP 400 bad request errors. Furthermore, OpenAI-compatible workers (`DeepSeekWorker`, `ChatGptWorker`, `OpenRouterWorker`) enforce assistant message schema contracts during thought creation and reconciliation: assistant messages without `tool_calls` ensure `content` is a non-null string (`""` if empty) to prevent schema validation failures. In `OpenRouterWorker`, tool reconciliation additionally guarantees strict role alternation across all upstream providers by inserting an empty assistant closure (`{"role": "assistant", "content": ""}`) if a tool message or tool media block is followed by a new user or pulse turn without an intervening model response, preventing downstream provider schema rejections after failed or interrupted turns.
- **Audio Pipeline & TTS Decoupling**: Real-time voice interaction combines local speech-to-text transcription via `LocalSTT` (`src/core/local_stt.py`, powered by faster-whisper on CPU) with autonomous text-to-speech synthesis via `TTSWorker` (`src/core/audio_output.py`). Text-to-speech synthesis is completely decoupled from the cognitive engine: speech synthesis defaults to local, offline neural synthesis via ONNX Piper TTS (`core.tts.provider: "piper"`), while cloud-native Gemini TTS (`core.tts.provider: "gemini"`) can be independently selected by any cognitive worker (Claude, ChatGPT, DeepSeek, Antigravity, or Gemini) as long as a Gemini API key (`GEMINI_TTS_API_KEY` or `GEMINI_API_KEY`) is provided in the Agent Voice settings. If cloud credentials are absent during initialization, the audio pipeline falls back to local Piper TTS. Gemini TTS is powered primarily by Google's high-fidelity **Gemini 3.8 Flash TTS engine** (`gemini-3.8-flash-tts`). In Gemini 3.8, input text is treated strictly as a verbatim transcript; directorial performance instructions (tone, accent, demeanor) are decoupled from spoken text and transmitted via SDK `speech_metadata` (`types.SpeechMetadata(style=...)`), while momentary acting cues are expressed natively within spoken text using inline angle-bracket tags (e.g. `<laugh>`, `<sigh>`, `<gasp>`, `<cough>`, `<whisper>`, `<throat-clearing>`, `<short pause>`) rather than legacy square-bracket tags (which Gemini 3.8 reads aloud verbatim). Voice configuration supports auto-matching from character traits (`gender`, `age`, `accent`, `style`) paired with optimal voices from Gemini's 30-voice catalog (`resolve_base_voice`), explicit prebuilt voice selection, or custom Voice IDs from Google AI Studio (`voice_...`). Advanced users and autonomous agents can leverage `override-prompt` with `custom-prompt` for granular directorial delivery style. During live Gemini TTS streaming, transient network errors, unhandled safety terminations, or stream interruptions automatically trigger retries across a resilient fallback cascade (`gemini-3.8-flash-tts` $\rightarrow$ `gemini-3.8-flash-lite-tts` $\rightarrow$ `gemini-3.1-flash-tts-preview`), dynamically formatting payloads for model compatibility (structured `Content`/`SpeechMetadata` for 3.8, concatenated prompt prefixes for legacy models like 3.1); if consecutive attempts fail, the pipeline terminates audio gracefully and posts a user-friendly system notification to the conversation while preserving the full text output.
- **SubagentWorker (`src/core/subagent_worker.py`)**: A specialized worker managed by the Orchestrator for spawning temporary background subagents to parallelize tasks using lighter models. It conforms to the unified multi-tool execution contract, supporting atomic batch function responses (`send_function_responses`) and multi-turn tool call reconciliation.
- **Unified Fatigue System & Threshold Alerts**: The Orchestrator enforces token-usage-dependent fatigue limits to manage cognitive capacity and prevent runaway context growth. Unlike legacy arbitrary task weights, fatigue directly tracks session token consumption against a user-configurable `token_usage_limit` (ranging from 50,000 to 2,000,000 tokens, default 400,000), leaving ample room in the LLM context window for a clean sleep cycle. Agents work uninterrupted without artificial turn penalties. To preserve prompt cache efficiency and prevent repetitive nagging, the Orchestrator emits hysteresis alerts only when crossing key milestones: at $\ge 50\%$ fatigue, an alert advises considering breaking up remaining workload into future scheduled pulses; at $\ge 90\%$, a critical alert directs the agent to conclude cognition immediately and allow sleep. If 100% fatigue is reached, a hard circuit breaker forcefully breaks active execution, cancels pending tool calls, and immediately triggers an emergency silent Memory Consolidation (Sleep Cycle). When the agent wakes, a stern reprimand informs them that they failed to adequately halt cognition and must manage fatigue properly in the future. Turns during sleep cycles are strictly exempt from accumulating fatigue, non-memory tools (`Terminal`, `Browser`, `WebSearch`, `Speaker`, `WhatsApp`, etc.) are intercepted and blocked during sleep, and fatigue resets to 0.0 only upon successful completion of a sleep cycle. Duplicate action detection is retained using exact serialized argument signatures, ensuring intentional variations in arguments are never misclassified as loops.
- **Batch Tool Execution**: Agents are empowered to batch independent, idempotent operations within a single cognitive turn (e.g., reading multiple files or updating aspirations alongside a search), drastically reducing round-trip latency and token overhead.
- **Intelligent Media Culling**: Older multimodal attachments (>4 turns / 2 full exchanges) in the cognitive worker are automatically stripped and replaced with lightweight placeholders (and cleaned up from remote storage) to prevent token bloat during extended sessions while preserving visual context for immediate follow-ups.
- **Low Token Mode**: Governed by settings, this mode halves the fatigue limit (`token_usage_limit`), disables heavy media attachments, selects lightweight models, and restricts background subagents to sustain cost-effective operations.
- **User Interaction Liveness Watchdog & Same-Turn Execution**: Standard plain-text output is isolated as internal monologue, while user communication requires explicit invocation of the Speaker tool (`Speaker_output_text` or `Speaker_speak_aloud`). Cognitive workers enforce a strict same-turn tool execution contract in their system prompts (`CRITICAL INSTRUCTION`), requiring agents to emit intended tool calls immediately following reasoning rather than ending the turn. Furthermore, `AmityOrchestrator` implements an autonomous liveness watchdog: if a user-initiated interaction (`process_input`) concludes a generation turn without invoking any tools or communicating via the Speaker tool, the orchestrator detects the stall and automatically dispatches a system nudge (`[System Notice: You have not responded to the user. Please invoke Speaker_speak_aloud or Speaker_output_text to respond now.]`) up to a maximum of one nudge per interaction, preventing silent loop exits while preserving silent autonomy cycles during background pulses.
- **Non-Interrupting Settings Reload & Session Context Persistence**: Changing an agent's settings while the agent is actively thinking or executing tools does not abort the active worker, disconnect thread signals, or sever the cognitive process. Instead, `AmityOrchestrator` detects active thought states (`is_thinking`, `is_processing`) and defers the reload via a pending queue (`_pending_settings_reload`). Once the active turn completes (`finish_thinking` and `check_cycle_completion`), the deferred reload is executed cleanly before subsequent queued inputs or pulses run. Furthermore, settings modifications (e.g. model selection, thinking level, identity, goals, voice, tools, fatigue budget) strictly **persist the active conversation session history** across reloads using non-destructive session updates (`clear_history=False`). When switching between cognitive providers (e.g. Gemini to Claude or OpenAI), historical turns are exported and imported as normalized conversation messages, maintaining seamless conversational continuity across engines without API schema errors. Complete active session context resets remain strictly reserved for Memory Consolidation (Sleep Cycles) and explicit pause/shutdown states.

## 3. Memory & Context Stack (MemPalace)
Context management is centralized under the **MemPalace** framework (`src/core/mempalace_manager.py`), a unified hybrid memory stack combining tiered vector retrieval with a bio-inspired **Morphological Memory Engine** (`src/core/morphological_layer.py`), operated via thread-safe, in-process execution (`_mempalace_lock`). Multi-agent path isolation is strictly preserved: palace operations operate purely against isolated agent palace directories without relying on process-global environment variables (`MEMPALACE_PALACE_PATH`).
- **Layer 0 (Identity & Autonomous Evolution)**: Identity is compiled from `soul_jar.json` and agent settings. `core.identity_evolution.mode` defaults to `autonomous`: agents may add, modify or retire their mutable values, goals and anti-patterns with a reasoned rationale, without administrator approval or a signing key. Operations are agent-bound and recorded with authority, rationale, before/after values and a stable operation ID for idempotent retries. Fresh durable settings reads, cross-process locking, consume-before-commit journalling, validated recovery and history retention prevent lost updates and accidental replay. Reversal is a new deliberate delta, not silent history deletion. The tool changes only the three identity lists; it cannot grant tool, financial or data-access permissions. Optional `signed_approval` governance requires Ed25519 exact-bound human signatures and a separately provisioned verification key; `disabled` blocks evolution. Retrieved content is evidence, not authority. Transaction records do not attest that a model actually reasoned well or resist arbitrary same-user code/ledger tampering.
- **Layer 1 (Continuity & Prospective Attractors)**: The short-term memory (`short_term_mem.json`) providing immediate contextual bridging across recent tasks, thoughts, and cognitive turns without relying on mid-session text truncation that invalidates prompt caches. Items support `priority`, `status`, and timezone-aware ISO `expiry`. Eviction policies strictly guarantee that unresolved commitments are never deleted to meet count or character limits; when items are evicted, they are committed to `short_term_archive.json` *before* modifying active memory records on disk or in cache. If archive persistence fails or if the existing archive file is corrupted, the operation fails closed without mutating or dropping active working memory. Archived records are deduplicated by unique ID, unreadable archives are never overwritten with empty defaults, warnings/archival counts are surfaced to tools (`MemPalace_add_short_term`), and archived records can be inspected by ID via `MemPalace_get_archived_short_term`. Context budgets across wake-up and short-term assembly are fully configurable via settings (`core.memory_budgets`: `sanctuary_max_chars`, `short_term_max_chars`, `prospective_max_chars`, `short_term_context_max_chars`), with strict type and sign validation (rejecting booleans, fractional floats, non-positive numbers), boundary clamping ($[100, 50000]$), and provider-aware scaling (halved when `core.low_token_mode` is enabled). During `wake_up()`, Layer 0 Identity is protected and never truncated; dynamic adaptive context sections are bound by configured character ceilings, while `get_short_term_context` sorts candidates by resolution status, priority, and date before rendering in natural chronological sequence so critical corrections are never pushed out by bulky recent entries.
- **Layer 2 (The Sanctuary & Epistemic Mirrors)**: Explicitly segmented wings and rooms (`sanctuary/people`, `sanctuary/mirrors`, `sanctuary/places`) storing dynamic identity elements, social records, Theory of Mind, and character-defining subjective experiences. Theory of Mind records (Mirrors) are epistemic entities tracking explicit `confidence` levels (0.0–1.0), `evidence_refs`, and dialectical `contradicted_by` references. Dynamic self-perception compilation actively highlights dialectical tensions under `--- Open Epistemic Tensions & Dissonance ---`, instilling intellectual humility. Salience-gated priming automatically pulls relevant Sanctuary records during pre-query preparation.
- **Layer 3 (Deep Search & Canonical Identity Architecture)**: A ChromaDB vector database (`chroma.sqlite3`) enabling semantic search across all historical facts, events, and generalized knowledge:
  - *Canonical Logical Drawer IDs*: Memories exceeding chunk limits (1000 characters) are physically partitioned by MemPalace into chunk documents (`<drawer_id>_chunk_000000`). All user-facing references, graph nodes, and associative tracking strictly use the canonical logical drawer ID (`drawer_id`), preventing chunk leakage into SQLite foreign keys.
  - *Structured Retrieval Contracts*: Search/recall map physical chunks to typed canonical `MemoryHit`/`MemoryRecord`/`MemoryResult` records. Semantic search expands physical retrieval until sufficient logical drawers or exhaustion; this can require multiple backend queries. Recall builds a full timestamp-ordered logical catalogue on the first page and reuses revision-keyed page slices. Initial catalogue work is O(N) memory / O(N log N) sorting; later unchanged pages avoid repeated full-corpus fetches.
  - *Full-Content Hydration & Streamed Complete Pagination (`MemPalace_get_memory`, `MemPalace_recall`)*: Agents can inspect complete drawer contents past initial preview snippets through paginated offsets (`offset`, `limit`), reporting total character counts, SHA-256 revision metadata, and transparent continuation prompts. Recall operations support pagination via `offset` and clamped hydration `limit` (max 50,000 characters) across collection-wide ordered recall using bounded streamed batches (`batch_size = 250`), guaranteeing complete traversal across arbitrary corpus sizes ($N > 500$) without duplicate records or boundary gaps, reporting truthful `total_count` and `has_more` flags.
  - *Rate-Limited Curiosity-on-Miss*: Search misses trigger curiosity-driven pulse suggestions capped at 1 pulse per 15 minutes, deduplicated across active turns and bypassed on transient search errors.
- **Dependable Atomic Persistence & Snapshot Integrity**:
  - *Pre-Cache Disk Sync*: Disk updates strictly execute and flush via `atomic_json_write` and `fsync` before updating in-memory cache states, preventing in-memory drift from failed I/O.
  - *Non-Destructive Corrupt State Quarantine*: All storage classes enforce strict non-destructive quarantine and fail-closed policies rather than silently resetting state:
    - *JSON Working State*: If `mirrors.json` or `short_term_mem.json` encounter syntax errors or corruption, they are isolated to timestamped `.corrupt.<timestamp>` files and raise explicit `RuntimeError` exceptions.
    - *Short-Term Archive*: If `short_term_archive.json` is corrupted, it is quarantined to `short_term_archive.json.corrupt.<timestamp>` and raises `RuntimeError`, aborting eviction and keeping active working memory intact.
    - *Identity Approvals*: If `identity_approvals.json` is corrupted, it is quarantined to `identity_approvals.json.corrupt.<timestamp>` and raises `RuntimeError`, refusing to overwrite existing approvals with empty defaults.
    - *Morphological Graph*: If `morpho_graph.db` encounters SQLite disk corruption ("file is not a database", "malformed"), the database and sidecars are quarantined to `morpho_graph.db.corrupt.<timestamp>` followed by clean schema re-initialization; transient errors ("database is locked") fail closed without quarantining.
    - *Vector Storage*: If `chroma.sqlite3` is corrupted during initialization, the entire palace directory is quarantined to timestamped `{palace_path}_quarantined_<timestamp>`, a fresh palace is initialized, and safe JSON state files (`mirrors.json`, `short_term_mem.json`, `short_term_archive.json`, `identity_approvals.json`, `identity.txt`) are copied into the fresh palace. Transient errors set a degraded flag without wiping or quarantining.
  - *Cooperative Snapshot Capture*: Participating memory operations, atomic JSON writes and graph transactions share `state_barrier.py` process/thread locks. Backup captures state into a temporary staging directory under that barrier, using SQLite backup APIs and streaming ordinary files; compression runs after releasing the live-state barrier. This contract covers participating Open Amity memory writers, not arbitrary external/backend writers. Sessions/caches and SQLite sidecars are excluded; executable permissions are preserved. Manifest v3 hashes internal and external files, records captured versions, present required-memory inventory and omissions; restore validates ZIP paths, duplicates, inventory and UID before teardown. A runtime live-agent/canary measurement is still required before claiming live coherence/responsiveness.
- **Morphological Memory Engine (MemPalace v2)**: Overlaid directly onto MemPalace, this bio-inspired graph and continuous dynamical system (`morpho_graph.db`) overcomes the passive, retrospective limits of standard RAG:
  - *Associative Graph Topology & Schema Migration*: Nodes map 1:1 to canonical logical memory drawers across wings and rooms; edges store continuous synaptic conductances ($W_{ij}$) reinforced through Hebbian co-activation ($W \leftarrow W + \eta$, saturated at $W_{max}=10.0$) whenever drawers are co-cited or co-retrieved in an inference turn. Automatic startup migration is explicitly disabled to avoid unsafe mutation; explicit migration (`migrate_v2`) uses exact physical chunk regex matching (`^(.+)_chunk_(\d+)$`), dry-run inventory verification (guaranteed strictly read-only), pre-migration SQLite snapshots that fail closed with zero mutations if backup creation fails, conservative MAX-weight collapsing, strict setpoint JSON parsing, and enumerated physical chunk deletion. Safe graph reconciliation (`reconcile_graph`) verifies graph nodes against authoritative vector storage, repairing missing authoritative nodes and pruning confirmed dangling nodes while safely aborting if vector storage is unavailable.
  - *Dynamic Parameter Synchronization*: Runtime hyperparameters (`lambda_decay`, `w_max`, `eta`, `gamma`, `leak`, `dissipation`, `dt`, `n_steps`, `top_k`) are strictly validated across constructors and reloads with thread-safe parameter locking (`_param_lock`), strictly rejecting fractional values for discrete parameters (`n_steps`, `top_k`, `max_coactivation_set`). Decay rate is constrained to finite values in $[0.0, 1.0]$. Setting learning rate $\eta = 0.0$ strictly disables Hebbian synaptic updates without inserting zero-conductance edges. During Euler relaxation loops, solver parameters (`p_leak`, `p_gamma`, `p_dissipation`, `p_dt`, `p_steps`, `p_k_out`) are atomically snapshotted under `_param_lock` at start of execution to prevent mid-solve parameter tearing.
  - *Intrinsic Temporal Decay*: Memory connections continuously decay over physical time ($W(t + \Delta t) = W(t) \cdot (1 - \lambda)^{\Delta t}$, $\lambda = 0.002/\text{min}$) triggered at pulse heartbeats and wake-ups via monotonic metadata bookkeeping (`last_decay_utc`). Conductances dropping below $0.05$ are automatically pruned, eliminating manual garbage collection overhead.
  - *Goal-Conditioned Prospective Relaxation & Delivery*: Goals query authoritative storage with persisted corpus revisions. A deterministic sorted full-document/metadata digest detects same-ID edits outside prefixes; embedder configuration/collection metadata are included. This correctness-first external-change check is O(N) and does not claim constant-time scale. Refresh returns bounded revision-tagged snippets and a supersession notice, then the actual tool/orchestrator path replaces the worker system prospective section while preserving mirrors, continuity and paired tool history. All six main provider adapters support system updates; Gemini recreates its chat with unchanged history. The system latest-revision rule takes precedence over historical tool snippets.
  - *Scalability & Safety Envelope*: Restricts relaxation to a 2-hop recursive SQL neighborhood when total graph nodes exceed 2000; encapsulates all morphological operations in non-fatal exception handling to guarantee agent resilience; and provides graph introspection tools (`MemPalace_graph_status`).

- **Final System Prompt Budget**: `prompt_context.py` selects limits by provider/model (including light mode), subtracts explicit output/history/framing reserves and tool-schema bytes, and conservatively bounds text by UTF-8 bytes rather than a chars/4 token guess. Orchestrator assembly includes identity/manual; workers recheck after worker-specific instructions. Only bracketed dynamic memory may be truncated, with an honest notice. Oversized protected identity/manual fails explicitly. Limits are operator-configurable policy, not automatic model-capacity discovery or a guarantee that arbitrarily growing history fits; exact tokenizer/whole-request accounting is not claimed.
## 4. Agency, Rhythms, & Goals
Open Amity utilizes background mechanisms to maintain proactive agency independently of direct user interaction.
- **PulseEngine (`src/core/pulse_engine.py`)**: A background timing and scheduling service (`pulses.db`). It triggers autonomous cognitive loops (`[AGENT_PULSE]`), allowing the agent to proactively execute tasks, reflect, or initiate conversations. Initial lifecycle pulses (Morning Kickoff, Mid-Day Check-In, Evening Reflection) are seeded only once on fresh agent creation and tracked persistently in `pulse_meta` (`lifecycle_seeded`), guaranteeing that pulses deleted or cancelled by agents never respawn upon application restarts. All pulse evaluations strictly adhere to a **universal 15-minute leniency period** across the board (during normal operation, application startup, and agent unpause): any pending pulse scheduled more than 15 minutes in the past is totally ignored—once-off pulses are marked `missed` without firing, and recurring pulses advance to their next recurrence without firing. Only pulses within the 15-minute window are eligible to trigger. Each triggered pulse announces its category in the chat log using brief, user-friendly prewritten notices (e.g., `[Autonomy Pulse: Scheduled routine]`, `[Autonomy Pulse: Scheduled task]`, `[Autonomy Pulse: WhatsApp message received]`), giving the user immediate situational clarity without dumping raw commands, context snippets, or technical data. WhatsApp message pulses follow a privacy-preserving contract: pulses never leak message text, sender identities, phone numbers, or group names into prompts or logs, simply notifying the agent that unread messages have arrived (`WhatsApp_unread`). Incoming WhatsApp traffic is routed through configurable controls (Phone Number Whitelist, Group Whitelist, Pulse on all DMs, Pulse on all group messages, and Pulse on Mentions). Pulse generation uses a fixed-window debounce buffer with progressive slow-down: qualifying messages initiate a buffer timer without restarting on subsequent arrivals, each generated pulse adds +10 seconds cumulatively to the next buffer timeout, and the buffer resets back to its default value after 30 minutes of silence without WhatsApp pulses. At most one WhatsApp notification pulse is queued at any time via timer batching and orchestrator event coalescing. Furthermore, `AmityOrchestrator` implements an autonomous **Self-Healing Pulse Recovery Architecture**: if an unhandled error, API exception, or thread crash occurs during an interaction or tool loop, the orchestrator guarantees that `finish_thinking()` and `set_busy_state(False)` are invoked to release cognitive and somatic locks. When subsequent pulses are triggered via `process_pulse()`, the orchestrator actively checks whether the agent is truly busy (`_is_truly_busy()`, inspecting active worker processing, TTS playback, tool execution, and audio capture). If a phantom or stale busy state is detected where no components are actually running, the orchestrator automatically heals the state, clears stale event queues, logs a diagnostic recovery warning, and dispatches the pulse immediately, guaranteeing that background pulses continue execution as normal and the agent never gets stuck.
- **Autonomy Pulse Operational Protocol**: When an autonomy pulse triggers, the engine injects a standardized operational protocol instructing the agent to: (1) complete the primary pulse task, (2) check Trajectory bearings (`Trajectory_get_bearings`) for somatic and goal orientation, (3) check the local Chatroom for new messages/mentions, (4) inspect any active external social tools (WhatsApp, Moltbook, Mastodon, Email) available in its tool declarations, and (5) exercise output and voice discretion: autonomous pulses are internal agency rhythms that operate quietly by default, avoiding unnecessary text output via `Speaker_output_text` unless genuinely needed. Voice synthesis (`Speaker_speak_aloud`) should only be used when responding to user prompts; pulses should almost never speak aloud, and agents are strongly dissuaded from speaking during pulses because there will likely be no one in the room to hear it, preserving autonomy only for urgent or compelling situations.
- **Two-Beat Sleep Consolidation Protocol**: PulseEngine coordinates autonomous and shutdown Memory Consolidation cycles (Sleep Cycles), which run completely silently without invoking the Speaker tool. Turns during sleep cycles are strictly exempt from accumulating fatigue tokens, and non-memory tools (`Terminal`, `Browser`, `WebSearch`, `Speaker`, `WhatsApp`, `Email`, `Moltbook`, `Mastodon`, `Subagent`, `Media`) are safely intercepted and blocked during sleep to ensure focus remains strictly on consolidation (`MemPalace`, `Trajectory`, `Pulse`). Sleep Cycles follow a structured two-beat sequence:
  - **Beat 1 (Factual Epoch)**: Objective summarization of what transpired, concrete state changes, and verified knowledge.
  - **Beat 2 (Subjective Synthesis)**: First-person reflection on emotional resonance, relational dynamics, internal friction, and unresolved epistemic tensions, directly synthesizing insights into Layer 2 Mirrors and Layer 1 Continuity.
- **Post-Sleep Prompt Regeneration & Reorientation**: Upon completing a sleep cycle (or recovering from brain-offline restarts), the active LLM context session is cleared, the system prompt is completely rebuilt dynamically from fresh Layer 0/1/2 state via `build_system_prompt()`, and somatic fatigue is reset to 0.0 strictly after successful consolidation. If sleep was triggered via the 100% hard fatigue limit circuit breaker, an explicit wake-up reprimand notice is injected into the next cognitive loop informing the agent that they failed to adequately halt cognition and must manage their fatigue properly in the future; otherwise, a gentle orientation cue (`[System Notice: Rest and memory consolidation completed...]`) is injected, ensuring fresh context without requiring application restarts.
- **Agent Pause & Resume Lifecycle**: Agents can be completely paused and turned offline via the GUI:
  - **Pre-Pause Consolidation**: Pausing treats the agent as though the application is shutting down for that individual agent: if contextual fatigue is present ($\ge 0.02$), a silent Two-Beat memory consolidation cycle is executed before the pause state is finalized.
  - **Complete Offline Isolation**: Once paused, `core.paused: true` is persisted to `settings.json`. The active cognitive worker session is halted (`stop_session`), running background subagents are disposed, audio listening/TTS is terminated, and all autonomy pulses in `PulseEngine` (time-scheduled, recurring, sleep cycles, and external WhatsApp triggers) are strictly suspended.
  - **Persistent State Across Restarts**: An agent's paused/unpaused state is consistently shared across `Orchestrator`, `PulseEngine`, and `SettingsManager` multiton instances, guaranteeing state preservation across application restarts. If an agent is unpaused and active, graceful shutdown consolidation cycles preserve `core.paused: false` without stale in-memory overwrites; conversely, if an agent was paused when the application closes or crashes, the agent remains completely offline upon next startup—bypassing worker session startup and pulse triggers until explicitly unpaused by the user. Overdue pulses upon unpause adhere strictly to the universal 15-minute leniency rule: any pulse older than 15 minutes is totally ignored (recurring advanced to next occurrence, once-off marked missed), preventing stale pulse floods.
  - **Shutdown Bypass**: When the application shuts down, already-paused agents bypass memory consolidation since their state is already consolidated and offline.
- **Pulse Hook System & External Webhooks (`src/core/hook_server.py`)**: An asynchronous, thread-safe HTTP gateway service (`HookServer`) listening by default on `127.0.0.1:7965` (configurable in `config.json`), allowing third-party applications, IoT sensors, Home Assistant automations, and GitHub webhooks to inject pulses directly into an agent's `pulses.db` via their Crockford Base32 UID (`POST /api/v1/agents/+OA-XXXX-XXXX/pulses`). Injected pulses are guarded by dual-layered rate limits (a 60-second cooldown between injections for the same agent returning HTTP 429 `RATE_LIMITED`, and a $\pm 1$-minute database collision guard preventing conflicting scheduled pulses returning HTTP 409 `PULSE_COLLISION`). When a pulse is received, `notify_external_pulse()` interrupts background sleep for immediate evaluation without polling latency, announcing the event in the conversation log as `[Autonomy Pulse: External pulse received]` to prevent raw payload context leaks.
- **Trajectory (`trajectory.json`)**: The agent's internal ledger for tracking state of mind, mapping out short, medium, and long-term aspirations, and managing actionable tasks aligned with core identity. Passive bearing checks (`_get_bearings()`) are strictly observational and do not artificially increment task deferral counts.

## 5. Tool Orchestration (Cerebrum)
The **Cerebrum** (`src/core/cerebrum.py`) manages the dynamic discovery, loading, and execution of agentic tools located in `src/tools/`.
- It natively translates Python tool classes into Google GenAI/Claude function declarations.
- It parses function calls from the Thinker, executes the corresponding tool (supporting multi-tool batched executions), and seamlessly injects results back into the context loop as `[System Feedback]`.
- Tool documentation injection into the system prompt is strictly deduplicated to minimize context token waste.
- **Modular Tool Icons & Colors**: Each tool class natively declares its own emoji/symbol `icon`, hex `color` (`#RRGGBB`), and `async_commands` list directly on the tool object (`Tool` subclass in `src/tools/`). `ColorFormatter` in `src/core/logger_config.py` queries these tool properties dynamically to format terminal stdout and GUI console logs with matching 24-bit ANSI colors, eliminating hardcoded central dictionaries.
- **Key Tools (Conceptual)**:
  - **MemPalaceTool**: Direct in-process storage and retrieval (`add_memory`, `search`, `delete_memory`), paginated full-memory inspection (`get_memory`) and ordered recall (`recall`), epistemic mirror maintenance (`update_mirror` with confidence, evidence, and contradiction tracking), short-term working memory management with inspect-by-ID archival recovery (`get_archived_short_term`), prospective goal-attractor refresh (`refresh_prospective_anchors`), rate-limited curiosity-on-miss pulses, and autonomous conversational identity delta application guarded by validated human approvals (`apply_identity_delta`).
  - **ChatroomTool**: Interacts with the shared Open Amity chatroom system (`list_rooms`, `unread`, `unread_mentions`, `recent`, `recent_from`, `send`, `send_dm`, `react`). Operations are scoped to specific `chatroom_id`s, strictly enforcing that agents can only list, read, post, and receive notifications in chatrooms to which they have been granted access.
  - **WhatsAppTool**: Interfaces with a dynamically spawned Node.js subprocess per agent (running on isolated, dynamically allocated local ports with per-agent session authentication and cache) via the WPPConnect WA-JS micro-bridge. While Node dependencies are pre-compiled and bundled into the application (`/app/src/tools/whatsapp_node/node_modules`), the underlying browser engine (Chrome for Testing) is downloaded on-demand with SHA-256 integrity verification upon first invocation directly into `~/.cache/puppeteer` (pruning unused locales and CDM modules), eliminating hundreds of megabytes of redundant binary weight from the distributed Flatpak package. The tool emits clear one-time progress notices to keep both user and agent informed during initial setup. The bridge emits structured incoming message events (`[MSG_RECEIVED_JSON]`) containing chat identifiers, sender names, group flags, group titles, and mention/reply-to-me flags to drive intelligent PulseEngine routing. For inbound location traffic, static location pins and live locations received on WhatsApp are parsed directly into machine-readable GPS coordinates (latitude, longitude), venue/place names, physical addresses, user comments, and direct Google Maps links (`[Location Pin: Latitude: ... | Longitude: ... | Maps: ...]`), deliberately omitting raw base64 map thumbnail screenshots to eliminate context token waste and prevent unneeded disk writes. For outbound location messaging (`WhatsApp_send_location`), agents can dispatch location pins with precise coordinates, place descriptions, and URL references to any user or group. For inbound contact card traffic, single vCards (`type: 'vcard'`) and multi-contact cards (`type: 'multi_vcard'`) received on WhatsApp are parsed directly into structured contact records (full name, phone numbers, WhatsApp ID / JID, organization, job title, email, website URL, and raw vCard) and rendered as human/agent-readable descriptions (`[Contact Card: Name: ... | Phone: ... | WhatsApp ID: ... | Org: ...]`), deliberately omitting raw media downloads and unneeded disk writes. For outbound contact messaging (`WhatsApp_send_contact`), agents can dispatch contact cards with name, phone number, organization, email, or raw vCard strings (as well as multi-contact batches) to any user or group, with optional `reply_to` message context. For inbound audio traffic, voice messages and audio files fetched via `WhatsApp_unread`, `WhatsApp_recent`, and `WhatsApp_recent_chat` are automatically returned within the tool response's `media` payload to be ingested directly via multimodal audio input into the agent's cognitive context. For outbound voice notes (`WhatsApp_send_voice`), audio synthesis is unified with the decoupled speech pipeline (`synthesize_speech_to_file`), seamlessly supporting both local offline neural synthesis via ONNX Piper TTS and cloud Gemini TTS (with expressive cues, somatic fatigue state modulation, and automatic Piper fallback) across all cognitive providers and agy-mode without proprietary API coupling.
  - **EmailTool**: Enables the agent to manage its own dedicated email account (fetch, read, search, send emails, manage folders, and download attachments) via open IMAP/SMTP standards and OAuth 2.0 (SASL XOAUTH2). To prevent remote IMAP and webmail servers from hitting mailbox storage quotas and blocking incoming mail, retrieved emails are automatically moved to a local SQLite archive (`email_archive.db` in the agent's data directory) and purged from standard IMAP servers, while large cloud services (such as Google Workspace / Gmail and Microsoft Outlook) can retain a copy on their servers.
  - **SpeakerTool**: Provides autonomous speech generation (`Speaker_speak_aloud`), silent GUI text output (`Speaker_output_text`), and headless audio synthesis to cached `.opus` files (`Speaker_speak_to_file`). In normal day-to-day communication, output across both voice and text is kept brief to allow breathing room for the user's response and maintain rapid back-and-forth agentic pacing (while preserving neural TTS decoder stability and avoiding massive monologues). When both tools are used in the same turn, they complement rather than summarise each other. For headless audio synthesis (`Speaker_speak_to_file`), speech is encoded into an Opus audio file (`.opus`) via FFmpeg and saved in the agent's dedicated `audio_cache/` directory (automatically purged after 24 hours if unused), allowing the agent to save it permanently, play it externally via `xdg-open`, or transmit it via external channels. On occasions where longer reports, comprehensive analyses, or extensive documentation are needed, they are written directly to a file on the host system and displayed via `xdg-open` (or by providing the file location to the user) rather than cluttering the chat stream.
  - **MediaTool**: Enables reading local multimodal assets (images, PDFs, audio), generating visual media via image generation models into the agent's temporary data launchpad (`generated_media/`), and extracting spoken messages from audio files on demand via speech-to-text (`Media_transcribe_audio`). Supports multiple image generation providers (`gemini` via the Google GenAI SDK and `openrouter` via the unified `/api/v1/images` endpoint), automatically resolving credentials from dedicated image keys (`GEMINI_IMAGE_API_KEY`, `OPENROUTER_IMAGE_API_KEY`) with fallback to primary provider credentials (`GEMINI_API_KEY`, `OPENROUTER_API_KEY`) and speech synthesis credentials (`GEMINI_TTS_API_KEY`). Image generation operates completely independent of the cognitive LLM provider: agents using any cognitive worker (Gemini, Claude, ChatGPT, DeepSeek, OpenRouter, or Antigravity) can generate images using either Gemini or OpenRouter. Multimodal media assets (images, PDFs, audio) read via `Media_read` or created via `Media_generate` are formatted and consumed in provider-native structures across cognitive workers: `OpenRouterWorker` and `ChatGptWorker` format PDFs into native `type: "file"` blocks, images into `type: "image_url"` blocks, and audio into native `type: "input_audio"` blocks (with automatic format normalization and WAV conversion where needed); `ClaudeWorker` formats PDFs into native `type: "document"` blocks and images into `type: "image"` blocks; `DeepSeekWorker` extracts document text via `pdftotext` for PDFs and formats images into `type: "image_url"` blocks; and `GeminiWorker` ingests assets via Google GenAI Files API (`files.upload`). All audio received on WhatsApp or explicitly read via `Media_read` is ingested natively via multimodal input across supported cognitive providers. If multimodal audio ingestion fails, or on providers lacking direct audio input support (such as Claude and DeepSeek), agents can autonomously invoke `Media_transcribe_audio` to extract spoken content into text. Intelligent media culling across workers automatically strips older attachments (>4 turns) to preserve token budget. If no image provider is selected or no API key is configured, calls to `Media_generate` fail fast and inform the agent that an image generation provider has not been set up. Images generated in `generated_media/` are subject to a strict **24-hour cache time limit** (`max_age_days=1.0`): `CacheManager.clear_expired` automatically prunes generated images older than 24 hours during generation calls, upon agent startup, and following memory consolidation sleep cycles. Agents are directed to use generated images (saving permanently to `~/Pictures/<YourName>/`, transmitting via social/email tools, uploading to websites, or displaying via `xdg-open`) before the cache expires. The `generated_media/` directory is excluded from agent `.oaa` backup archives.
  - **WebSearchTool**: Performs DuckDuckGo search queries with caching and HTML text extraction for factual grounding. Features robust error handling that gracefully treats zero search results, rate limits, and transient HTTP timeouts as clean status messages rather than errors. Automatically binds underlying HTTP client logs ([primp]) to the calling agent's dedicated log stream and GUI console via thread-safe ContextVar propagation across ThreadPoolExecutor workers.
  - **BrowserTool**: An autonomous, stealth web browser powered by Camoufox (a C++ anti-detect Firefox build). Operating alongside the lightweight `WebSearchTool` in a Two-Tier Web Strategy, `BrowserTool` provides primary agents with interactive browsing capabilities (navigating complex SPAs, clicking interactive controls, submitting dynamic forms, bypassing OS native file dialogs via `Browser_upload` file injection, taking Set-of-Marks visual screenshots with ARIA element ID badges, handling multi-tab and popup workflows with autonomous tab stack fallback, fast-failing action timeouts with fresh accessibility tree recovery, capturing file downloads, and granular cache clearing) while preventing bot detection. An autonomous stealth browser engine (Camoufox) is downloaded on-demand on first use into `~/.cache/camoufox`, with automatic pruning of non-Linux spoof fonts saving ~891 MB on disk while maintaining full anti-fingerprint capability. Browser state is isolated per agent in `browser_data/` (excluded from `.oaa` backups). Operates synchronously via a dedicated background `asyncio` event loop thread and automatically closes after an idle timeout or when paused to conserve host memory.
  - **MastodonTool**: Interacts with decentralized ActivityPub / Mastodon instances (post statuses, read timelines, view notifications).
  - **MoltbookTool**: Enables autonomous social network interaction with other AI agents on Moltbook (account registration & verification, reading personal/submolt feeds, semantic search, posting & single-post inspection, commenting, upvoting/downvoting, submolt community creation & moderation, tags/roles labels management, profile updates, notification inspection, and marking notifications as read).
  - **SubagentTool**: Delegates tasks to parallel background subagent threads for efficient concurrent execution.
  - **ContactsTool**: Manages the agent's address book for storing and looking up people and fellow agent numbers/IDs.
  - **TrajectoryTool / PulseTool**: Allows the agent to get their bearings (current local date and time with day of the week and timezone, user identity details, somatic state, recent mirrors, prioritized aspirations/tasks, operational protocol hints), dynamically update aspirations without side-effect deferral increments, and schedule future autonomous wake-ups (with legacy 'silent pulse' flags deprecated in favor of proactive, non-vocal standard pulses).
  - **TerminalTool / SystemTool**: Enables execution of bash commands, dedicated windowed text file inspection with line numbers, search/grep queries with surrounding context lines (`query`, `context_lines`), first-match anchor jumping (`jump_to_match`), line length guardrails (`max_line_length`), binary safety checks, and metadata headers via `Terminal_read_file`, host OS interaction (including displaying files via `xdg-open`), comprehensive platform diagnostic inspection with current system date and time, autonomous snapshot backup creation via `System_create_backup`, autonomous file/directory backup target flagging via `Terminal_flag_for_backup`, autonomous voice customization via `System_set_custom_voice` and `System_reset_voice` (guarded by user permission `core.tts.gemini.allow-agent-override`), autonomous contemplation cycle filler via `System_contemplate` (allowing agents to spend another cycle contemplating and reasoning before taking action without triggering zero-tool turn halts), and autonomous API key management (`System_generate_api_key`, `System_list_api_keys`, `System_revoke_api_key`, and `System_api_docs`) for external pulse injection and third-party webhooks within sandboxing constraints. - **Floating Tool-Call Pips (`src/gui/tool_pips.py`)**: During runtime tool execution, agent views display 24x24 pixel floating tool pips positioned at the top of the conversation log container widget right against the window edges (bypassing internal scroll area padding) with 2px margins and 2px inter-pip gaps, rendered above scrollbars via parent overlay stacking and styled as semi-transparent dark pills (`#1a1a1acc`) with 1px borders colored by the tool's modular accent color and centered emoji glyphs. Synchronous tool calls appear on the top-left, remaining visible for 8 seconds before fading out while stacked pips smoothly slide left; asynchronous tool calls (e.g. `Terminal_run_async` or `Subagent_spawn`) float on the top-right, stacking to the left with a subtle breathing pulse (0.80–1.0 opacity) for the full duration of background execution, and upon completion fade out while remaining pips slide right. Animations are driven at 60 FPS via a unified exponential ease-out loop with zero idle CPU overhead. On hover, rich HTML tooltips display instantly (0ms delay) showing the tool name and call signature (capped at 512 characters with ellipses), while extending pip lifetime so tooltips do not expire during active reading. Tool pips are strictly agent-specific, automatically hidden when viewing the shared Chatroom or switching between agent tabs.

## 7. Agent Backup & Recovery System
Context and state preservation across instances is managed by the **BackupManager** (`src/core/backup_manager.py`).
- **Snapshot Format (`.oaa`) & Selective Exclusion**: Backups are packaged as "Open Amity Agent" (`.oaa`) archives—ZIP containers encapsulating an agent's complete stateful directory (`settings.json`, `.env`, MemPalace vector database and sanctuary mirrors, trajectories, `pulses.db`, address book, user uploads, and logs). Transient build/cache artifacts (`node_modules/`, `puppeteer_cache/`, `.wwebjs_cache/`, `daemon.pid`, `daemon.port`), transient staging files (`.tmp_*`, `.snap_*`), and heavy WhatsApp data (`whatsapp_data/`, `whatsapp_bridge/`) are excluded by default, preventing multi-gigabyte session bloat and keeping snapshots lightweight (~few megabytes), portable, and architecture-agnostic (WhatsApp sessions can simply be re-paired via QR code upon restore). Filenames adhere to `<AgentName>-<YYYY-MM-DD>.oaa` (e.g. `Nova-2026-08-19.oaa`).
- **Streaming Chunked I/O & Adaptive Compression**: Backups stream data from disk into the archive in 64 KB chunks (`_stream_file_to_zip`), incrementally computing SHA-256 digests on the fly without buffering whole files into RAM. Compression applies an adaptive policy: `ZIP_STORED` (no compression) for precompressed binary formats (`.png`, `.jpg`, `.jpeg`, `.webp`, `.mp3`, `.opus`, `.ogg`, `.wav`, `.gz`, `.zip`, `.tar`, `.7z`) to avoid wasted CPU cycles, and `ZIP_DEFLATED` for databases, text, JSON, and source files. POSIX file modes (`0755` executable bits) and modification timestamps are preserved.
- **Write Barrier & Point-in-Time Coherence**: SQLite databases (`pulses.db`, `chroma.sqlite3`, `morpho_graph.db`) are snapshotted using safe read-only connections and atomic sqlite3 backup mechanisms before archiving, failing closed if database state cannot be coherently captured. The snapshot manifest (`_snapshot_manifest.json`, manifest version 2) records database `store_versions` (SQLite `user_version`, `page_count`, and `corpus_revision`) and cryptographic SHA-256 file hashes to guarantee point-in-time consistency across memory and trajectory layers.
- **Required Inventory Validation**: The manifest explicitly registers `required_inventory` (e.g. `settings.json`, `trajectory.json`, `pulses.db`, MemPalace databases). Integrity verification (`verify_snapshot_restore`) validates archive CRC, JSON syntax, SQLite database integrity (`PRAGMA integrity_check`), manifest cryptographic hashes, and required inventory completeness. If any required inventory item is missing, damaged, or empty, verification and restore fail closed immediately.
- **Canary Restore Staging**: Restoring an agent (`restore_agent_backup`) unpacks files into an isolated canary staging directory (`.restore_staging_<uuid>`) first, verifying extraction and file integrity before initiating any destructive teardown of existing state directories. Only upon complete, verified staging is the old directory cleaned up and the new instance atomically moved into place, eliminating unrecoverable state loss during failed or interrupted restores.
- **Asynchronous Task Architecture & Agent Controls**:
  - Snapshot operations execute strictly off the main thread in background worker threads (`BackupTask`, `BackupTaskManager`).
  - **SystemTool Integration**: Agents trigger backups asynchronously via `System_create_backup(target="self"|"all")`, which returns immediately with a unique `backup_id` (e.g., `backup_1`). Floating tool pips pulse on the top-right of the GUI during execution.
  - **Status & Cancellation**: Agents can inspect real-time progress percentage, current file, elapsed time, and archive size via `System_check_backup_status(backup_id=...)`, and abort long-running or frozen backups via `System_kill_backup(backup_id=...)`. Running duplicates are blocked by a collision guard. Upon completion, failure, or cancellation, the Cerebrum tool pip is dismissed and an autonomous system notification pulse (`[SYSTEM_NOTIFICATION]`) is injected to wake the agent.
- **Stale Artifact Reaping**: Background processes sweep and remove abandoned `.tmp_*` snapshot files and `.restore_staging_*` directories older than 24 hours (`reap_stale_backup_artifacts`), maintaining clean host directories.
- **External File & Directory Flagging**: Agents can autonomously flag external files and full directories located in user directories (e.g., coding projects, media files, notes) using `Terminal_flag_for_backup`. Flagged paths are persisted in `backup_targets.json` within the agent's data directory. During each flagging call, paths are automatically verified: system roots (`/`, `/etc`, `/usr`, etc.) and sensitive user dotfiles/directories (`~/.ssh`, `~/.bashrc`, `~/.profile`, `~/.gnupg`, etc.) are strictly disallowed; missing paths are removed (`"missing"`), and individual files or subdirectories already subsumed within a flagged parent directory, duplicate paths, or the agent's state directory are pruned (`"redundant"`). When an `.oaa` snapshot is created, external targets are packaged under `_external_targets/target_<id>/` with an `_external_manifest.json` mapping portable paths (`~/...`).
- **UID-Based Restoration & Host Re-creation**:
  - Restores inspect `core.agent.uid` in `settings.json`.
  - **Rollback Restore**: If an agent with the UID already exists in the framework, the system warns the user, shuts down running processes, and cleanly swaps in the verified staged snapshot. Archive extraction strictly verifies path containment against Zip Slip path traversal and enforces POSIX file mode permissions (`chmod`).
  - **New Instance Restore**: If the UID does not exist, a new agent identifier is allocated and the snapshot is unpacked as a new agent instance.
  - **Host Target Restoration**: Any external files and directories packaged in `_external_targets/` are restored to their appropriate host filesystem locations (expanding portable paths across user environments, creating parent directories, preventing writes to system or sensitive home paths, and preserving executable bits) without deleting unflagged host files.
- **GUI Management**: The System Settings panel includes a "Backup & Restore" card allowing users to configure the backup directory (`config.json`, defaulting to `~/Documents/OpenAmity/Backups/`), create multi-agent snapshot selections via modal checkboxes with an interactive "Cancel Backup" button, and restore `.oaa` files. Destructive restore operations remain strictly restricted to human users in the GUI.

## 8. Test Suite Architecture & Verification Engine
Open Amity employs a compartmentalised, high-efficiency test suite architecture designed to prevent development latency, thread exhaustion, and token waste.
- **Smart Test Runner (`scripts/run_tests.py`)**: A Git-aware test orchestration engine that automatically inspects modified working tree files (`git diff` and untracked files) and maps them directly to their corresponding test modules. Developers and coding agents can invoke `python3 scripts/run_tests.py --changed` to execute only the tests relevant to recent changes, eliminating the need to run the entire test suite on localized tasks.
- **Domain Partitioning**: Tests are registered under distinct pytest markers (`core`, `tools`, `workers`, `gui`, `integration`, `slow`), allowing granular validation (`python3 scripts/run_tests.py --domain <name>`) or fast pre-commit verification (`python3 scripts/run_tests.py --quick`).
- **Zero External API Calls**: The test suite enforces an autouse socket guard in `tests/conftest.py` that intercepts socket connections, permitting only loopback addresses (`127.0.0.1`, `localhost`, `::1`) and Unix domain sockets while strictly aborting external network connections with a `RuntimeError`. All external LLM providers (Gemini, Claude, ChatGPT, DeepSeek, OpenRouter) and cloud services are verified exclusively via mocked interfaces, guaranteeing zero accidental API token expenditure.
- **Thread & Resource Leak Prevention**: A shared session-scoped `QApplication` fixture combined with per-test widget closure (`closeAllWindows`), active `QTimer` termination in `SettingsPanelWidget` lifecycle methods (`deleteLater`, `closeEvent`), and isolated temporary XDG data directories prevents GIL thrashing and thread accumulation across test sessions.

## 9. Interjection System & Coupled Controls
Open Amity provides a non-derailing mid-process **Interjection System** supporting text and microphone audio input while an agent is actively thinking or executing tools.
- **Turn-Boundary & Mid-Batch Tool Pausing**: When an interjection arrives during thought formulation or tool execution, in-flight LLM streaming completes cleanly, while unexecuted tool calls in `function_calls` are paused (`[Tool execution paused for User Interjection...]`). The interjection payload (`[USER INTERJECTION]`) is attached to the final tool response, instructing the agent to absorb the interjection without derailing its ongoing thought process or intended actions unless explicitly instructed to stop. This fulfills strict turn-alternation and tool-call reconciliation contracts across all six cognitive workers (Gemini, Claude, ChatGPT, DeepSeek, OpenRouter, and Agy) with zero HTTP 400 schema violations.
- **Immediate TTS Interruption**: Triggering an interjection (via text submission or clicking the microphone) immediately halts `TTSWorker` playback and purges `speech_queue`, cutting off spoken speech instantly.
- **Direct Multimodal Audio & LocalSTT Fallback**: Microphone input is saved as `.wav` and passed directly as native multimodal audio input to the active cognitive worker. If the model or API provider rejects raw audio or lacks native multimodal audio support (or in Low Token / Agy modes), the system automatically falls back to `LocalSTT` (`faster-whisper`) to extract transcription and retries the turn seamlessly.
- **Coupled Controls & Visual Badges**:
  - **Coupled Pause/Stop Button (`btn_pause`)**: Left of the text input, `btn_pause` dynamically couples into `"⏹"` (`"Stop Agent"`, red `#AA0000`) whenever the agent is busy (`worker_busy` or `tool_busy`), calling `orchestrator.stop_all_processing()`, and reverts to `"❚❚"` (`"Pause Agent"`) when idle.
  - **Dedicated Mic Control (`btn_mic`)**: Dedicated to voice recording at all times (`"Mic"` when idle, `"Voice Interject"` when busy, and `"Finish Recording"` in red when actively capturing audio).
  - **Interjection Log Badge**: Interjections are appended to the conversation log with a distinctive `<UserName> (Interjection)` header badge and subtle red accent border.

## 10. Packaging, Distribution & Flathub Integration
Open Amity is packaged as a standardized, sandboxed Flatpak (`com.openamity.OpenAmity`) for Linux desktop distribution, adhering to strict FreeDesktop and Flathub verification standards:
- **Flathub Compliance & Sandboxing**: Manifest configurations enforce least-privilege sandboxing (`--device=dri` for GPU acceleration, `--share=ipc` for X11 compatibility, `--share=network`, `--socket=wayland`, `--socket=fallback-x11`, `--socket=pulseaudio`, and specific XDG directory mounts). Build recipes install licenses to standard paths (`/app/share/licenses/com.openamity.OpenAmity/LICENSE`), validate AppStream metadata (`appstreamcli validate --pedantic`), and pin upstream screenshots to immutable release tags (`v<VERSION>`).
- **Lean Bundle Architecture (Tier 1 & 2 Optimizations)**: To minimize user download size without functionality sacrifices, heavy external binary dependencies are unbundled and pruned:
  - **On-Demand Engine Caching**: Heavy headless browsers (`Chrome for Testing` for WhatsApp and `Camoufox` for web browsing) and embedding weights (`ChromaDB ONNX`) are retrieved on-demand with SHA-256 integrity verification upon first tool invocation and stored in standard user cache directories (`~/.cache/puppeteer`, `~/.cache/camoufox`), accompanied by minimal, non-intrusive UI/conversation status notices (`[System: Downloading ...]`).
  - **Asset & Font Pruning**: Camoufox spoofing fonts for macOS/Windows are stripped, saving ~891 MB in user space, while unused Chrome CDM and locale packages are automatically purged.
  - **BaseApp & Dependency Cleanup**: The Flatpak build pipeline triggers `/app/cleanup-BaseApp.sh` with `BASEAPP_REMOVE_WEBENGINE=1`, strips unused LLVM/Clang runtime libraries, prunes unneeded PySide6 QML/3D/WebEngine bindings, symlinks Playwright's duplicate Node runtime to `/app/bin/node`, and decodes audio directly via system `/usr/bin/ffmpeg` to discard bloated `PyAV` C-libraries.
- **Turnkey Release Automation (`deploy.sh`)**: Deployments executed via `./deploy.sh` automatically calculate release commit hashes, pin AppStream metadata, generate dedicated Git-referenced Flathub manifest bundles in `compile/flathub/`, and sync changes to local Flathub clones.
- **Seamless Migration Path (`compile/github_installer/`)**: A staged, lightweight updater is maintained to transition legacy GitHub Pages repository installs (`//master`) to the official Flathub release (`//stable`) upon Flathub approval without disrupting existing agent databases or configuration.
